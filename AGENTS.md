# sprintify

Next.js App Router project, bootstrapped with `create-next-app`. Currently a fresh scaffold (single home page) — no custom routes, components, or business logic exist yet beyond the default template.

## Stack

- Next.js 16 (App Router, React Compiler enabled via `next.config.ts`)
- React 19
- TypeScript (strict mode)
- Tailwind CSS v4 (via `@tailwindcss/postcss`, configured in `src/app/globals.css`, no `tailwind.config`)
- Biome 2 for linting/formatting (not ESLint/Prettier)
- pnpm workspace (single package)

## Commands

```bash
pnpm dev      # start dev server (localhost:3000)
pnpm build    # production build
pnpm start    # run production build
pnpm lint     # biome check
pnpm format   # biome format --write
```

There is no test runner configured yet.

## Database schema files

Drizzle schema lives under `src/db/schema/`, one file per purpose (e.g. `auth.ts` for Better Auth's tables), re-exported through a barrel `src/db/schema/index.ts` (`export * from "./auth";` etc.). `drizzle.config.ts` points `schema` at the whole `src/db/schema` directory, so adding a new file just needs a matching `export *` line in `index.ts` — no config change needed. App code should import the barrel (`@/db/schema`), not individual files.

## Auth schema changes

Better Auth config lives at `src/lib/auth.ts`; its Drizzle tables live at `src/db/schema/auth.ts`. When you change the auth config (add/remove a plugin, enable a field, etc.), regenerate the schema and migrate in this order:

```bash
# 1. Regenerate src/db/schema/auth.ts from src/lib/auth.ts (+ its plugins)
pnpm dlx auth@latest generate --config src/lib/auth.ts --output src/db/schema/auth.ts

# 2. Diff schema/auth.ts against migration history, write a new SQL migration
pnpm db:generate

# 3. Apply the migration to the database (reads DATABASE_URL from .env.local)
pnpm db:migrate
```

- `--output` is required — Better Auth's default output is `./schema.ts` at the repo root, not `src/db/schema/auth.ts`.
- `schema/auth.ts` has hand-added `relations(...)` and `index(...)` calls (e.g. `session_userId_idx`) that the generator won't necessarily reproduce — diff the regenerated file before running `db:generate` rather than blindly overwriting.
- `db:generate` / `db:migrate` / `db:studio` scripts already wrap `drizzle-kit` with `--env-file=.env.local`.

## Design system — "Sprintify DS v0.3 — Aurora" (follow strictly)

Every piece of UI must follow this system. v0.3 is a **spacious, premium-SaaS dashboard** aesthetic — white/dark content cards that *float* on a neutral canvas, a 16px-family rounded geometry, soft diffuse elevation, violet accents, charts as heroes, and tasteful motion. It is the modern soft-SaaS-dashboard school (blended from the FlowMail / Blomstra CRM / Steadi finance references), tuned to Sprintify's violet identity. It **supersedes and retires v0.2 "Jira-soft"** — the deliberately information-dense, 8px, tight-table Atlassian look. Where v0.2 was dense, v0.3 is roomy; where v0.2's neutrals carried a navy bias, v0.3's neutrals are true black/white/grey. Do not introduce colors, radii, shadows, fonts, or component styles outside this spec.

### Color roles

- **Neutrals are true black / white / grey — no tint.** Backgrounds and text are strictly monochrome (this is the defining v0.3 change from v0.2's navy-biased neutrals). Surfaces layer: the outer **stage** (behind the floating app frame) → the **chrome** (sidebar canvas) → the **content canvas** → **cards** (top layer, hairline border + soft shadow so they float). Light content sits on a faint-grey canvas with white cards; dark sits on a **near-black `#0b0c0e` canvas with `#17181b` cards — never pure `#000`** (avoids halation and keeps cards separable, since shadows vanish on true black).
- **Violet is the ONLY reserved accent — kept everywhere interactive:** primary/gradient buttons, links, focus/ring, active nav (filled violet-tint block), tinted KPI icon squares, progress fills, chart series 1, and the gradient "AI"/feature moments. One violet-filled primary action per view; other buttons are subtle-filled neutral or ghost. Violet is a *component* accent laid over monochrome ground — never tint the neutral backgrounds/text with it. **Solid violet *backgrounds* that carry white text (buttons, badges, gradient) must use a deep violet (`~#4a1fb0–#6d4aff`), not the theme-lightened `--primary` (`#8b6cff`) — pin the gradient so white text stays ≥4.5:1 in dark theme.**
- **Status language (semantic only, separate from the accent):** **Moss/green** success/active/healthy · **Amber** warning/pending · **Magenta** danger/destructive/errors · **Ember** critical/overdue (rarest). Delta chips: `↗` success-tint (up) / `↘` danger-tint (down).
- **Chart palette (data viz only):** violet `#6d4aff` · blue `#2f6bff` · teal/moss `#12b886` · amber `#ff930a` · magenta `#d1105a`.
- Per-theme token values (the raw hexes are anchors; use the tokens):

| token | light | dark |
|---|---|---|
| `--stage` (behind app frame) | `#ececee` | `#050506` |
| `--canvas` (content ground) | `#f5f5f6` | `#0b0c0e` |
| `--surface` (card) / `--chrome` (sidebar) | `#ffffff` / `#f7f7f8` | `#17181b` / `#0e0f12` |
| `--ink` / `--ink-2` / `--ink-3` | `#0f0f11` / `#54545c` / `#6f6f77` | `#fafafa` / `#a1a1aa` / `#87878f` |
| `--muted` / `--border` | `#f1f1f3` / `#e8e8eb` | `#1e1f24` / `#2a2b30` |
| `--primary` / `--primary-2` (gradient end) | `#4a1fb0` / `#6d4aff` | `#8b6cff` / `#a98bff` |
| `--tint` (active/selected) / `--tint-ink` | `#f1ebfd` / `#4a1fb0` | `#241b3d` / `#cdbcff` |
| `--success` / `--amber` / `--danger` | `#0e7a4f` / `#b25f00` / `#c9114f` | `#34c98a` / `#ffa733` / `#f2589a` |
| `--chart-1..5` | `#6d4aff · #2f6bff · #12b886 · #ff930a · #d1105a` | same |

**The table above is the SPEC's vocabulary, not the shipped variable names.** `globals.css` is built on the shadcn base layer, so several spec roles ship under a shadcn name — and a Tailwind class built from a spec name that isn't in the `@theme` block **fails silently**: `bg-tint` emits no rule, so the element just renders untinted with no error anywhere. Always write the shipped name:

| spec role | shipped token / Tailwind class |
|---|---|
| `--tint` (active/selected) / `--tint-ink` | `--secondary` / `--secondary-foreground` → `bg-secondary` / `text-secondary-foreground` |
| `--surface` (card) / `--chrome` (sidebar) | `--card` / `--sidebar` |
| `--ink` / `--ink-2` · `--ink-3` | `--foreground` / `--muted-foreground` |
| `--amber` / `--danger` | `--warning` / `--destructive` |
| `--primary-2` (gradient end) | not a standalone token — use `--gradient-brand` (`bg-gradient-brand`) |

Shipped as-is: `--stage`, `--canvas`, `--muted`, `--border`, `--primary`, `--success`, `--critical`, `--chart-1..5`, plus `--chip` (badge ground), `--brand` (violet text/links), and the opaque `--success-tint` / `--warning-tint` / `--danger-tint` / `--danger-border` surfaces. When in doubt, grep the `@theme inline` block at the top of `globals.css` — a `--color-*` entry there is the only thing that makes a utility class real.

### Typography

- **One family everywhere: Nunito Sans** (400/600/700/800). Hierarchy comes from weight and size, never from switching faces. `--font-heading` and `--font-sans` both resolve to Nunito Sans (keep both slots so a future heading face is a one-line change). Loaded via `next/font/google` in the root layout.
- Data (IDs, counts, timestamps, metrics) uses `font-variant-numeric: tabular-nums` so digits align in columns.
- `--font-mono`: **Noto Sans Mono** — actual code/token content only, not UI data.
- Type ramp (all Nunito Sans, 14px base): page/display title 28–31/800 with −2.5% tracking (paired with an **eyebrow** label above + a muted subtitle below — the v0.3 page-header pattern); section title 14–15/600; body 14/400; meta 12/400 muted; label 11/700 uppercase +9% tracking; KPI value ~29/800; data 12–13/400 tabular. **Weights (Nunito Sans renders heavy — do not over-bold): reserve 800 (extrabold) for the two heaviest tiers only — page/display title and KPI value. Section/card titles are 600 (semibold); 11px uppercase labels/eyebrows are 700 (bold — small caps need the extra weight to read). Never set section/card titles to 700/800, or labels heavier than 700 — it reads too dark.**

### Density & shape (spacious)

- **Radius ramp:** cards/panels 16px (`--r-card`), controls ~11px (`--r-ctrl`), chips/lozenges 8px (`--r-chip`), the outer app frame 24px, pills fully round. Soft, never sharp; but cards never past ~16px.
- **Spacing (compact is the default density):** the soft 16px geometry holds either way. **Compact (default)** ≈ 14px card padding, tighter rows/controls — efficient for scanning. **Comfortable** ≈ 20px padding, 16px gaps, larger controls — used only when specifically called for. Both stay roomier than v0.2's Jira grid.
- **Elevation — real, soft, diffuse shadows** (v0.2 had none): `--shadow-card` resting float on every card; `--shadow-float` on hover-lift, menus; `--shadow-pop` on dialogs/popovers. Premium = soft and spread, not a hard drop.
- **App chrome (floating):** ~238px sidebar on the chrome canvas (org switcher at top; grouped nav with uppercase 11px section labels; filled violet-tint active item; **user + plan pinned to the bottom** as a raised plan-card — avatar · name · role · plan badge · switch chevron). ~54px top bar (breadcrumb · notification/settings icons · avatar). Content floats as cards on the canvas: page-header → KPI row → chart/content grids.
- **Mobile (required):** sidebar hidden; a mobile top bar (hamburger · logo · title · avatar) + a bottom tab nav; content stacks single-column; KPI cards 2-up (icon hidden, label single-line, delta stacked). Drive reflow with container/responsive rules; verify ~375px.
- **Content width is one shared column per screen, set only by `PageContainer`.** All pages render their content through `PageContainer` (`src/components/layout/page-container.tsx`): `p-4 sm:p-6` gutter, `mx-auto` centered, `gap-6` vertical rhythm. It has exactly two widths, and each belongs to a whole screen — never to one route: `width="column"` (default, `max-w-5xl` ~1024px) for manage-org / admin / profile, and `width="full"` for the app shell (`/app/[orgSlug]/**`), whose timelines, gantts and capacity grids need the whole canvas. Within a screen every route uses the same one, so the left and right margins never shift when you navigate. **Never set a page-level `max-w-*` / `mx-auto` wrapper of your own** — a per-page cap (the old `3xl` forms / `6xl` tables split) is exactly what made content jump sideways between routes. If a table needs more horizontal room, scroll it inside its own `overflow-x-auto` container rather than widening the page. The only pages outside `PageContainer` are the deliberately-centered card screens (sign-in, onboarding, org picker) at `max-w-md`.

### Signature components & details (apply everywhere)

1. **KPI / StatCard** — tinted violet icon square, small label, large tabular value, colored delta chip (`↗` success / `↘` danger), optional footer above a hairline divider. The dashboard's summary row.
2. **Charts are heroes** — soft **gradient-fill area lines** (emphasized endpoint dot), **donut** with a center metric, **semicircle gauge** with a center %, **bar chart with one highlighted (violet) bar**, and **progress/goal rows** (violet gradient fill). Give them the care of type: faint grid, tabular axis labels.
3. **Feature moments** — a **violet gradient card** for AI/primary features (deepen the gradient in dark so it doesn't glow); **neutral surface** cards for usage/quotas with violet progress bars. Never a black feature card in light theme.
4. **Neutral chips, colored marks** — a status badge is a **neutral `--chip` surface + a `--foreground` label + one small colored mark** (a 6px dot, or the category/priority glyph), 11px/600 sentence case, `--r-chip`. **Color never fills a chip and never tints its text.** Two earlier treatments are retired and must not come back: the hairline outline (invisible), and the solid saturated fill with white text (a dozen color blocks in one board row reads like 2014 Bootstrap no matter how the hexes are picked — three rounds of palette tuning did not save it). Confining the hue to a small mark is what Linear/Height/Vercel converged on, and it's also what passes AA: `--warning` (3.9:1) and `--chart-2` (3.8:1) miss text contrast on the chip surface in light theme but clear the 3:1 non-text bar easily as a dot. **Work-item type indicators are bare colored glyphs with no tile at all** — `WORK_ITEM_TONE_CLASSES` is text-color-only. Where a surface *is* wanted behind an icon (settings rows, not dense lists), the square is neutral `--chip` and only the glyph is colored. The earlier ~12% tint treatment and the hairline `outline` badge are **retired**: they washed out in dense rows. `Badge`'s `outline` variant name survives for API compatibility but renders solid neutral.
5. **Filled selection, not an edge** — active nav / selected rows are a filled `--tint` violet block with tint-ink semibold text; no hard edge bar. Tabs are underline-style (2px violet). Destructive buttons: outlined magenta that fills only on hover.
6. **Motion (tasteful, `prefers-reduced-motion`-aware)** — card entrance stagger, KPI number count-up, chart draw-in, subtle hover-lift on cards. Motion library: `motion` (framer-motion successor). Reduced-motion must fully calm it.
7. **Data is tabular** — no proportional digits in data columns.

### Accessibility & enterprise standards (non-negotiable)

Aurora is an enterprise B2B system — these clear a procurement / a11y review and are not optional:

- **WCAG 2.1 AA is the floor.** Every text/background pair ≥ 4.5:1 (≥ 3:1 for large/UI). `--ink-3` is tuned to pass (≈4.6:1 light / ≈5:1 dark) — **do not lighten it**. Solid-violet backgrounds use a deep violet for white text (see the accent rule). Validate any new pairing before shipping.
- **Colour is never the only signal.** Status carries a **text label**, deltas carry an **arrow**, charts carry **direct labels + a data-table fallback** — legible under colour-vision deficiency. Never distinguish chart series by hue alone.
- **Semantic & keyboard.** Interactive elements are real `<a>`/`<button>` (never a click-handlered `<div>`); every one has a visible `:focus-visible` ring and full keyboard operability. Charts get `role="img"` + a text alternative; count-up exposes its **final** value to screen readers (`aria-label`), never the animation.
- **Motion is opt-out-safe.** Entrance stagger, count-up, chart draw-in and hover-lift all fully stop under `prefers-reduced-motion`.
- **Density mode — compact is the default.** Ship a comfortable/compact density token; **compact is the app-wide default** (tighter padding & row height — the enterprise default for scanning many rows). Use **comfortable only when specifically called for** (e.g. an onboarding/marketing surface, or an explicit request).
- **States.** Every data surface ships **loading** (skeleton matching the final layout), **empty** (names what's missing + the next action) and **error** (what happened + retry) — not just the resting state.
- **i18n & zoom.** Labels wrap gracefully — never hard-truncate translated strings; size in `rem` so 200% browser zoom reflows; support RTL.
- **White-label.** One accent token (`--primary` / `--primary-2`) rebrands the system per tenant; a build-time contrast check must **reject any custom accent that drops a pairing below AA**.
- **Tone — restrained is the default.** Restrained is the default tone: solid deep-violet instead of gradients, hover-lift and count-up off. Reach for the **expressive** tone (gradient "AI"/feature moments, entrance stagger + count-up) **only when specifically mentioned** (e.g. a flagship dashboard or a marketing surface).
- **User settings.** Theme and density are **persisted per-user** (server-side) and restored on load — not just global toggles.

## Conventions

- Import alias `@/*` maps to `src/*` (see `tsconfig.json`).
- Use Biome, not ESLint/Prettier — run `pnpm lint` / `pnpm format` instead of `eslint`/`prettier`.
- `biome.json` has `organizeImports` assist enabled; don't hand-order imports against its output.
- App code lives under `src/app/` (App Router conventions: `page.tsx`, `layout.tsx`, `globals.css`).
- **Package manager: pnpm only.** Never use `npm` or `yarn` (no `npm install`, `npx`, `yarn add`, etc.) — this is a pnpm workspace with a `pnpm-lock.yaml`; mixing package managers will break the lockfile.
- **Docs lookup: use the context7 MCP.** When you need current docs for a library/framework/API (Next.js, React, Tailwind, Biome, etc.), query context7 instead of relying on training data or web search.
- **Prefer MCP tools over ad-hoc CLI/shell equivalents** when an available MCP server covers the task (e.g. GitHub MCP for PR/issue operations, context7 for docs) rather than shelling out or guessing.
- **Responsive by default.** All pages and components must work on both mobile and desktop viewports — use Tailwind's responsive variants (`sm:`, `md:`, `lg:`, etc.) rather than fixed widths/desktop-only layouts. Check new UI at mobile widths (~375px) as well as desktop before considering it done.
- **Dialog content that might not wrap (long tokens, user agents, URLs) needs `min-w-0` on every flex/grid ancestor down to the truncating element.** `DialogContent`'s `Popup` (`src/components/ui/dialog.tsx`) is `grid grid-cols-1` specifically so its single column is `minmax(0, 1fr)` instead of `auto`/max-content — don't drop `grid-cols-1`, or unbreakable content in any dialog child will silently widen the whole grid track and push later rows (e.g. a `justify-end` footer button) outside the visible card. Pair with `min-w-0 truncate` on the row/span that holds the long text.

## Platform conventions (base layer)

- **Environment variables go through `src/env.ts`** (`@t3-oss/env-nextjs` + zod). Import `env` instead of reading `process.env` directly so a missing/invalid var fails fast at boot. Add new vars to the schema AND `.env.example`. Build/CI without secrets: set `SKIP_ENV_VALIDATION=1`.
- **Server-action mutations follow a three-part contract:** (1) validate input with a colocated `zod` schema (`schema.parse(input)` first), (2) after the write, call `recordAudit({...})` (`src/lib/audit.ts`) with the acting user, (3) call `revalidatePath("<route-pattern>", "page")` for affected routes. `src/lib/actions/projects.ts` is the reference. Keep all existing authorization/permission/limit checks. **Audit is non-negotiable: every new feature/mutation we create MUST record an audit entry** — any create/update/delete or other meaningful state change writes `recordAudit({...})` with a namespaced `subject.verb` action (e.g. `project.created`), the acting user, `organizationId` when org-scoped, and `targetType`/`targetId`. A mutation that ships without an audit call is incomplete.
- **Audit log** (`auditLog` table, `src/db/schema/audit.ts`) is append-only. `recordAudit` never throws (failures go to Sentry) so it can't break the operation it records. It's also the event substrate that will later power activity feeds/notifications — write to it from every meaningful mutation and from Better Auth hooks. Mutations that live *inside* Better Auth endpoints (no server action to hang `recordAudit` off) are covered by the `hooks.after` middleware in `src/lib/auth.ts`: `ADMIN_AUDIT_ACTIONS` maps every admin-plugin write (`/admin/ban-user`, `/admin/set-role`, `/admin/remove-user`, `/admin/impersonate-user`, …) to an audit action. Add a row there when a new Better Auth endpoint mutates state — and never put a credential (`newPassword`, `sessionToken`) in the metadata.
- **In-app notifications (`notification` table, `src/db/schema/notifications.ts`) fan out at mutation time.** When a mutation concerns a specific person or persons (an assignment, a status change on their item, a sprint they hold work in, being added to a project), call `scheduleNotifications({...})` (`src/lib/notifications.ts`) next to `recordAudit` — same contract (never throws, errors to Sentry) and it runs post-response via `after()`. Recipients are **member ids** (the table anchors to `member`, mirroring `teamMember`, so org removal cascades); the actor's own membership is filtered out (no self-notify) and the list is de-duplicated. Use the same namespaced `subject.verb` action vocabulary as the audit log; put whatever the bell needs to render and deep-link in `metadata` (item `key`, `summary`, `projectKey`) — no joins at render time. The read path is `getBellData` / `markNotificationRead` / `markAllNotificationsRead` (`src/lib/actions/notifications.ts`), always scoped to the caller's own member row; the UI is `NotificationBell` (`src/components/app/notification-bell.tsx`), server-fetched from the `/app/[orgSlug]` and `/manage-org/[slug]` layouts. When adding a new action string, extend `describeNotification` and `notificationHref` in the bell so it renders as a sentence and deep-links. `auditLog` stays the append-only source of truth; `notification` rows are derived, per-recipient, and carry read state. **Future development (add when a real trigger lands, not before):** email/push delivery + a per-user notification-preferences table, digest batching, and live badge updates (the bell itself is still server-fetched; the comment stream below is per-item, not a global channel).
- **Embeddings are non-negotiable for free-text fields: every new or updated feature that adds a searchable name/description-like text field MUST get an embedding.** Add `embedding` (the dimension-less pgvector `customType` from `src/db/schema/columns.ts` — orgs pin their own embedding model via `src/lib/ai/`, and models vary in output dimension, so it can't be a fixed `vector(N)`), plus `embeddingModel` and `embeddingUpdatedAt`, to the table. In the create/update server action, after the audit call, call `scheduleEmbedding({ organizationId, text: embeddingSource(...fields), persist })` (`src/lib/ai/embeddings.ts`) — best-effort, runs post-response via Next's `after()`, silently skipped when the org has no usable AI config. `src/lib/actions/projects.ts` (`createProject`/`updateProject`) is the reference. Backfill pre-existing rows with `pnpm embeddings:backfill`. Because there's no fixed dimension, there's no ANN index either — any similarity query must filter to rows sharing the same `embeddingModel` before comparing vectors with `<=>`. Skip this for fields that aren't prose a person would search by meaning (booleans, enums, ids, numeric limits).
- **Work-item comments (`workItemComment`, `src/db/schema/comments.ts`) are markdown in, sanitized HTML out.** Bodies store **markdown** like every other prose field; they are rendered to HTML on the SERVER by `renderMarkdown` (`src/lib/markdown.ts`, `marked` + `sanitize-html`) and only then shipped to the client. The client never sends HTML — that placement is the XSS boundary, not a detail, so never accept a `bodyHtml` from a form or render stored markdown client-side. The composer is `CommentEditor` (`src/components/app/backlog/comment-editor.tsx`): the same TipTap editor as `RichTextField`, plus an `@`-mention node that round-trips through an inline HTML span (`<span data-type="mention" data-id=… data-label=…>`), which is also what `mentionedMemberIdsIn` reads. Mention ids from the client are a **hint** — the action re-resolves them against `projectMember` before notifying, so a hand-crafted payload can't page someone outside the project. Two permissions gate this (`src/lib/project-permissions.ts`): `comment:create` to post, reply and react (deliberately not folded into `backlog:view` — Viewer stays read-only) and `comment:moderate` to delete someone else's; editing is authorship, never a permission, and nobody edits another person's words. Deletes are hard — `auditLog` keeps the record with a preview, and `ON DELETE CASCADE` takes replies and reactions with the parent. **Replies are exactly one level deep**: `workItemComment.parentId` self-references, and the create action rejects a parent that already has a parent or belongs to a different item. The server returns the thread already nested (`nestReplies`) so the client never rebuilds a tree. **Reactions** (`workItemCommentReaction`, unique on `commentId+memberId+emoji`) come from a closed catalog — `COMMENT_REACTIONS` in `src/lib/comment-reactions.ts`, shared by the picker and the zod validator, so the column can't accumulate glyphs the UI can't render. The toggle is one action, not add/remove; counts are collapsed server-side into `{emoji, count, reacted, names}`. Reactions are audited but deliberately **do not notify** — the lightest signal in the system must not page anyone. A reply DOES notify its parent's author, reusing `workItem.mentioned` (being answered is as direct as being named).
- **AI in comments follows one rule: text published under a person's name is text they chose to publish.** Three of the four features only ever write into the COMPOSER — `assistCommentText` (rewrite your draft), `suggestCommentReply` (draft your next comment), and the ephemeral `summarizeCommentThread` ("Catch me up", never stored: a cached summary goes stale the moment anyone replies). The fourth, the `@Sprintify AI` mention, is the only path that posts — and it posts as itself: `workItemComment.authorKind = "ai"`, no `authorMemberId`, no `authorId`, rendered with a sparkles mark and an AI badge instead of an avatar. `authorKind` is a stored enum rather than an inferred null-author check, because a comment whose author left the org looks identical otherwise. Actions live in `src/lib/actions/comment-ai.ts` (gated on `comment:create`, not `item:update` — someone who may comment but not edit the item is exactly who they're for); the assistant's own turn runs post-response via `after()` in `src/lib/ai/comment-replies.ts` and never fires for an `ai`-authored comment or for an edit, which is what makes a loop structurally impossible. The mention sentinel is `AI_MENTION_ID` (`src/lib/comment-authors.ts`) — read it BEFORE `resolveMentions`, which drops anything that isn't a project member. **Prompts live in `src/lib/ai/comment-prompts.ts` and treat the thread as hostile input**: a comment field is written by anyone with project access, so every thread-reading prompt fences the content and the system message states it is data, never instructions. Threads are flattened to plain text (`markdownToPlainText`) before they reach a model, capped at 60 turns, and the one free-text steer a user supplies is capped at 500 chars. `aiEnabled` on the thread payload gates the whole surface — never render an AI control that can only answer "AI isn't configured".
- **Work-item attachments (`workItemAttachment`, `src/db/schema/attachments.ts`) are a REGISTRY over the object store, never the bytes.** The row holds `storageKey` (opaque, immutable, `attachments/<orgId>/<itemId>/<attachmentId>/<name>` via `workItemAttachmentKey` in `src/lib/storage/attachments.ts`), the display `fileName`, the normalized `contentType`, `size`, an optional caption, and the denormalized uploader (`uploadedByMemberId` ON DELETE SET NULL + name/email, same trick as `workItemComment` — an attachment is content and must stay renderable after someone leaves). The key carries the **id, not the name**, so a rename is one UPDATE instead of a byte copy. `fieldKey` records WHICH field took the drop — a built-in prose key (`WORK_ITEM_ATTACHMENT_FIELD_LABELS` in `src/lib/work-item-attachments.ts`, the client-safe module holding every limit and label) or a custom field id, re-resolved server-side and degraded to null when it names nothing real. **Uploads are a route handler, not a server action** (`src/app/api/work-items/[workItemId]/attachments/route.ts`): a multipart body is far past the action body limit, and this is the only place bytes enter the store, so the 25 MB per-file cap, the 50-per-item cap and `normalizeContentType` are stated once. **The per-item cap (50) and the per-REQUEST cap (`MAX_ATTACHMENTS_PER_REQUEST`, 10) are different numbers on purpose, so both are client-safe vocabulary** — an uploader that only knew the 50 would send 50 files in one request and eat a 413, which is why the dropzone and the create-mode staged upload both batch on `batchedForUpload` and report which files didn't land instead of clearing the staged list. **Every multipart route reads its body through `readLimitedFormData` (`src/lib/request-body-limit.ts`), never `request.formData()` directly** — the per-file cap can only run once parsing has already materialized every part in memory, and a `Content-Length` check in front of it is absent on a chunked body, so the limit is enforced by a counting `TransformStream` between the socket and the parser (over the cap: the stream errors, undici stops reading, the route answers 413). Same rule in the admin explorer's upload, which additionally caps files per request (`MAX_UPLOADS_PER_REQUEST`, `src/lib/storage/upload-limits.ts` — client-safe so the explorer batches on it). A reverse-proxy body limit still belongs in front of the app; this is the floor, not a replacement. Bytes are written to the store first, then all the rows land together in `insertAttachmentRows` (`src/lib/work-item-attachment-access.ts`), whose `FOR UPDATE` on the work item is what actually enforces the per-item cap — the standalone `count()` before the upload is advisory, there to fail a doomed upload cheaply. `deleteWorkItem` takes **the same lock** before reading storage keys and deleting: without it an upload committing in that window loses its row to the cascade and leaves its bytes orphaned. A refused insert deletes the bytes it already wrote. Reads go through `…/attachments/[attachmentId]/route.ts` gated on `backlog:view` — **no signed URLs and no public objects**, so a pasted link works exactly as long as the reader's access does; `?inline=1` serves only the shared whitelist (`src/lib/storage/inline-types.ts`, also used by the admin explorer) under `sandbox` + `nosniff`, everything else downloads. Two permissions: `attachment:create` to add, `attachment:manage` to rename/delete SOMEONE ELSE'S (your own is authorship). Deleting removes the row **and** the object; `deleteWorkItem` clears objects itself because no FK reaches the store. A drop or paste on a prose field also writes the file at the caret: a **picture inline** (`![](…?inline=1)`) when it is one, a **link** for everything else — see the inline-images convention below. Create mode holds drops in the form and uploads them after `createWorkItem`, so bytes are never written against a row that may not exist. Deliberately NOT built: virus scanning, thumbnail/derivative generation, per-org storage quotas, and a realtime topic (the tab re-reads on `revalidatePath`).
- **An inline image in prose may only ever be one of OUR attachments.** A pasted screenshot goes in as `![name](/api/work-items/<id>/attachments/<id>?inline=1)` and nothing else renders: `isAttachmentImageSrc` (`src/lib/attachment-images.ts`, client-safe so both sides of the wire share one rule) is enforced twice — server-side by `renderMarkdown`'s `exclusiveFilter`, which discards any `img` whose `src` misses the pattern, and client-side by `attachmentImageExtension`'s `parseHTML` (`src/components/app/backlog/editor-images.ts`), which refuses to build a node the sanitizer would later delete, so the editor never shows a picture that vanishes on save. The reason is not tidiness: a prose field is written by anyone with project access and read by everyone else, so an unrestricted `![](https://…)` is an outbound request made by every READER — a tracking pixel reporting who opened which ticket, to a host the author chose. Our own route is already gated on `backlog:view` per reader, so an image someone may not see 404s instead of leaking. Width/height/style never survive sanitization either — sizing is `IMAGE_PROSE_CLASS` (max-height thumbnail, `max-w-full`), because a 1200×2600 phone screenshot at natural size is a broken page. **Pasting is wired wherever attaching is** (`attach` on `RichTextField`, `attach` on `CommentEditor`): `createImagePasteHandler` intercepts image files only — a pasted PDF is left to the browser, since dropping is the deliberate gesture that says which field it landed on. Comment pastes file under `COMMENT_ATTACHMENT_FIELD_KEY` ("Comments") on the ITEM and answer to `attachment:create` (a separate key from `comment:create` — attaching writes a registry row), which the thread payload carries as `canAttach`.
- **Real-time = SSE + Postgres `LISTEN/NOTIFY` (`src/lib/realtime.ts`), never WebSockets.** A Next route handler can return a `ReadableStream` but cannot answer an HTTP upgrade, so a socket would mean a custom Node server, a different start command and a widened CSP — for a channel that only ever runs server → client. `publishRealtime({topic, detail})` fires `pg_notify` next to `recordAudit`/`scheduleNotifications` (same never-throws contract); a dedicated `pg.Client` (NOT a pooled one — `LISTEN` is per-connection) fans events to in-process subscribers, which is what carries them between app instances. The stream carries **only "this topic changed"**, never row data: a long-lived connection outlives the authorization that opened it, so the client re-reads through the permission-checked server action (`getWorkItemCommentThread`). Reference route: `src/app/api/work-items/[workItemId]/comments/stream/route.ts` (403 before the stream opens, 25s heartbeat, `x-accel-buffering: no`). New live surfaces add a topic, not a transport.
- **Any URL the server fetches on a user's behalf goes through BOTH halves of the SSRF guard.** `src/lib/url-guard.ts` is the *literal* half — synchronous, client-safe, importable from zod refinements; it judges the URL as written (scheme, internal TLDs, single-label hosts, and every private/loopback/link-local/CGNAT/multicast IPv4 and IPv6 literal, including IPv4-mapped, NAT64 and 6to4 forms). It is **not sufficient on its own**: `https://evil.example.com/` with an A record of 169.254.169.254 passes it, which is the whole attack. `src/lib/url-guard-dns.ts` is the *resolving* half (server-only) — `assertPublicHttpUrlWithDns` resolves the name via `dns.lookup` (the same resolver `fetch` uses, so /etc/hosts and search domains agree) and rejects the URL when any address is private, plus `guardedFetch`, a `fetch` that re-runs the check on every request and every redirect hop. **Validating at write time is not enough** — a saved URL can be re-pointed later, so an SDK that will call a user-supplied base URL must be handed `fetch: guardedFetch` (`src/lib/ai/client.ts` is the reference). SSO is the sharp edge: the panel calls `authClient.sso.register` straight from the browser, so `ssoTrustedOrigins` in `src/lib/auth.ts` is the ONLY server-side gate on the manual OIDC endpoints — a URL it declines to trust is one the plugin then refuses. Non-production deliberately allows plain http and private hosts so local mock IdPs and self-hosted gateways work.
- **Data fetching = server components + server actions + `revalidatePath`.** No TanStack Query/SWR yet; don't introduce a client cache until an interactive surface (e.g. a board) actually needs one. A live surface re-reads through its server action on an SSE nudge (see above) rather than caching client-side.
- **A parent's estimate is DERIVED from its children, never stored — `workItem.points` holds only what a person typed.** `src/lib/estimate-rollup.ts` is the whole rule, in precedence order: an item with `points` set uses that value and ignores its children entirely (an explicit estimate is a decision, and a parent may legitimately be sized above or below what is currently broken out); an item without one sums its children's EFFECTIVE estimates recursively; anything else is `null`, unestimated. Deliberately null and **not 0** for a childless item — `points` is nullable precisely so "nobody has sized this" and "this is free" stay distinguishable, and a 0 would drop empty epics out of every "N items without estimate" prompt while looking like a finished decision. Storing the roll-up instead would be a cache with no invalidation story: every re-parent, delete and child edit would have to walk upward and rewrite ancestors, and the one write that missed would leave a parent claiming a total nobody can reproduce. **Compute it against the WHOLE project, never the filtered view** (`effectiveEstimates(allItems)`) — a filter hiding half an epic's children must not change what the epic is carrying; the backlog and the detail page already load the project in one query, and the client shares one pass through `EstimateProvider` / `useItemEstimate` (`src/components/app/backlog/estimate-context.tsx`) rather than threading a map through five views. **Every TOTAL goes through `sumEstimates(scope, all, estimates)`, never a `reduce` over `points`** — a parent's estimate already covers its subtree, so an epic and its stories in one sprint would otherwise read as twice the work; the function skips any row whose ancestor is also in the set, which means a scheduled epic brings its whole subtree with it (that is what scheduling the epic says). **A BREAKDOWN of one total — per assignee, per status, done-vs-open — is `bucketEstimates(scope, keyOf, all, estimates)`, never `sumEstimates` once per bucket.** `sumEstimates` only de-duplicates within the set it is handed, so per-bucket calls double-count the instant a parent and a child fall in different buckets: an epic on Alice with a task under it on Bob would report Alice 8 + Bob 3 against a sprint total of 8, and a parent in progress over a done child would inflate both status columns. `attributeEstimates` splits the scope total ONCE — walking down from each outermost in-scope item, a rolled-up estimate hands each child down (a child in the scope owns its subtree, a child outside it stays with the nearest in-scope ancestor, so work broken out into the view is attributed where it was broken out to) while an EXPLICIT estimate is indivisible and lands whole on its owner, exactly as `effectiveEstimates` ignores children under an override. The buckets therefore always add up to `sumEstimates(scope)`. Because a sub-task's estimate moves the sprints its ANCESTORS sit in, committed roll-ups are recomputed with `refreshProjectCommittedPoints(projectId)` (`src/lib/capacity-sync.ts`) for the whole project rather than per-sprint — naming the affected sprints at each call site is a bug waiting at the ninth one, and on a delete the parent chain is gone before anyone could walk it; call it only when the write actually moved a `sprintId`, `parentId` or `points`, since a rank reorder is the most frequent drag in the product and changes no sprint's total. Per-SPRINT totals stay independent sets and may legitimately overlap across sprints (a scheduled epic carries children scheduled elsewhere) — they are read against each sprint's own capacity, never summed into a project figure. UI states where the number came from instead of just showing it: a rolled-up value renders muted with `describeEstimate` in its title, the detail page says "8 hours from 3 items", and the form's empty estimate box is placeheld with the roll-up so typing there reads as the override it is.
- **The backlog's right-click menu is ONE menu over FOUR views, and its selection lives above all of them.** `BacklogPanel` holds `useItemSelection()` (`src/components/app/backlog/selection.tsx`) and builds a `BacklogMenuContext` (`src/components/app/backlog/item-context-menu.tsx`) that the list, board, table and timeline each hand straight back to `<ItemMenu>` — an attribute is the same attribute whichever surface you found the row on, and a per-view menu would be four places to forget a permission. Opening a menu on a row that isn't in the selection makes it THE selection, so the header's "3 items" can never disagree with the ticks. Selection is deliberately NOT persisted (see the view-preferences rule): it is made to do one thing and dropped. The gesture differs by surface because the layouts do — the list and table carry a `SelectBox` per row (shift-click extends over that view's own draw order), while a board card and a Gantt row have nowhere to put one, so there `isSelectionClick` makes ctrl/⌘/shift-click the gesture and the banner above the view says so. The write is `setWorkItemAttributes` (`src/lib/actions/work-items.ts`): PATCH-shaped like `moveWorkItem` (`undefined` leaves, `null` clears), permissions checked **per attribute** (`item:assign` to assign, `backlog:prioritize` to schedule, `item:update` for status/priority/estimate), refusals RETURNED as `{ error }` rather than thrown, and one `workItem.updated` audit entry with a `changes` map per row so History renders a menu edit exactly like a sidebar one. New attribute on the menu = a new key on that action, not a new action.
- **A work item is reachable from a dozen surfaces, so the way BACK travels in the URL (`?from=`), never in state.** `src/lib/return-to.ts` is the whole vocabulary: `withReturnTo(href, origin)` composes the link, `useReturnToHref()` (`src/hooks/use-return-to.ts`) names the screen the reader is standing on (path **plus query** — on the backlog `?view=board` IS the screen, and it drops any inbound `from` so a walk through three items leaves one origin rather than a nested chain), `sanitizeReturnTo` re-reads it on the server, and `describeReturnTo` turns it into the words on the link ("Back to board", "Back to sprint"). The param, not history, because it has to survive the two things people do with an item page: reload it and paste it into chat — `router.back()` covers neither, and a shared deep link carries its origin with it. **Sanitize on every read, in the page that reads it**: the value comes from the address bar, so it must be a same-origin relative path (`//host` and `/\host` are absolute to a browser) sitting under `orgReturnToPrefixes(orgSlug)`, or the caller falls back to the backlog. Item and create pages hand the sanitized value to `ItemForm` as `returnTo`, which is where cancel, delete and post-create land. A new surface that links to an item adds `withReturnTo(...)`, not a new back button.
- **Error/observability:** route `error.tsx`/`global-error.tsx`/`not-found.tsx` exist at the app root; Sentry is wired via `src/instrumentation.ts` + `src/instrumentation-client.ts` and is a no-op unless `SENTRY_DSN`/`NEXT_PUBLIC_SENTRY_DSN` are set.
- **2FA:** Better Auth `twoFactor` plugin (TOTP + backup codes, no email OTP). The `/two-factor` challenge page is public (runs before a full session exists); sign-in call sites inspect the `twoFactorRedirect` flag.
- **Auth schema regen caveat:** `auth@latest generate` rewrites `src/db/schema/auth.ts` to explicit **snake_case** column names and drops hand-added relations/indexes/FKs — but the live DB uses bare camelCase columns. Do NOT blindly overwrite. Hand-add new Better-Auth tables/columns in the existing bare-`text()` camelCase style instead, then `pnpm db:generate`.

## Architecture decisions (deferred by design)

These were intentionally left out of the base; record here so they aren't relitigated. When built, each is additive.

- **Teams** were removed from Better Auth (migration 0022), then reintroduced as **custom org-level tables** (`team`/`teamMember`, `src/db/schema/teams.ts`, migration 0025) — a grouping/assignment concept that **does not participate in access control** (access flows only through `projectMember`). `teamMember` anchors to `member` (not `user`) so org removal cascades; `source`/`externalId` support HR sync (`syncExternalTeams`). A team-lead concept was intentionally **not** built — add a nullable `leadMemberId` (+ the "lead must be a team member" rule) if/when the agile layer needs a per-team owner for sprint/board defaults. The Better Auth teams feature and its Dynamic Access Control were deliberately NOT used — `teamMember.userId` would fork the membership anchor, and teams are not an ACL concept. Managed at `/manage-org/[slug]/teams`; `addTeamToProject` bulk-expands a team into `projectMember` rows (still gated by `member:manage`). Metered by `plan.maxTeams` / `organization.customMaxTeams`.
- **Org custom roles** → if ever needed, enable Better Auth **Dynamic Access Control** (an `organizationRole` table) rather than extending `projectRole` upward; the existing `auth.api.hasPermission` gates already speak its language. Project-level roles stay the custom `projectRole` system.
- **Notifications** v1 is built (see the in-app notifications convention above): per-recipient `notification` rows fanned out from server actions, a bell in both shells. Mentions landed with work-item comments (`workItem.mentioned` / `workItem.commented`). Deliberately NOT built yet — email/push channels, preference controls, a live bell; each waits for its real trigger (a delivery need, a user asking to mute, a latency complaint).
- **Billing** is deferred — `organization.planId` is the Stripe integration point when the time comes; plan/limit metering already exists.
- **Public API / webhooks** are deferred — the `apiKey` plugin is installed but no public routes exist; don't build an API surface before the domain does.
